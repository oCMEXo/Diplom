# 5. Тестирование и безопасность

## 5.1. Уровни тестирования

| Уровень | Инструмент | Где | Тестов | Что проверяет |
|---|---|---|---|---|
| Модульные и сервисные | Vitest | `apps/api` | 133 | auth, проекты и роли, приглашения и гости, файлы, чат, запуск кода, WebSocket-хаб и присутствие, пересылка событий из Redis, импорт из GitHub (разбор ссылок, загрузка, отбор файлов, запись в документ Yjs) и отправка изменений (имитация GitHub: изменённые и новые файлы, конфликты, новая ветка, права, ошибки токена, предпросмотр без побочных действий), ветки (у каждой свои файлы и правки, повторное открытие без загрузки, имена со `/`, событие всем участникам, права и проверка имени), терминал (билет с файлами активной ветки, права), поиск по содержимому файлов (строка и столбец совпадения, без учёта регистра, только активная ветка без корзины, досок и `node_modules`, лимиты и признак усечения, права) и код доступа к запуску |
| Модульные | Vitest | `infra/local-host` | 9 | прокси тестового хостинга: отдача сайта, `/api`, WebSocket `/collab` и `/terminal`, кеш, ошибка при недоступном API |
| Модульные | Vitest | `apps/collab` | 5 | проверка прав доступа к документу при подключении |
| Интеграционные с реальным Docker | Vitest | `apps/runner` | 46 | параметры песочницы, выполнение кода в настоящих контейнерах, обработка задач очереди; терминал: протокол WebSocket (билеты, пересылка ввода и вывода, лимиты), bash с TTY в настоящем контейнере (node и python с файлами проекта, нет сети, запись только в свои папки, Ctrl+C) |
| Модульные | Vitest | `apps/web` | 57 | модель доски (Yjs), экспорт в SVG, стили чужих курсоров, цвета и аватары |
| Смоук-тесты стенда | Vitest | `bench` | 10 | обе системы сходятся во всех сценариях исследования на малых размерах |
| Сквозные (E2E) | Playwright | `e2e` | 22 | два настоящих браузера работают с живой системой |

Всего 282 теста; статический контроль — `tsc --noEmit` (строгий режим) и ESLint
по всем пакетам. Тесты API и runner работают с настоящими PostgreSQL, Redis и
Docker, а не с заглушками: сервис, который «проверен» на моках, не доказывает,
что работает миграция, транзакция или флаг `docker run`.

Все автоматические проверки запускаются в CI (`.github/workflows/ci.yml`):
линтеры, типы, тесты с поднятыми PostgreSQL и Redis, затем отдельное задание
E2E, которое устанавливает Chromium и запускает runner.

## 5.2. Сквозные сценарии (Playwright)

1. Двое открывают один файл; текст, набранный одним, появляется у другого.
2. Ссылка-приглашение с ролью «только чтение»: наблюдатель видит правки, но
   его собственный ввод не доходит до владельца.
3. Сообщение в чате доходит до другого участника; список «в сети» показывает
   двух человек.
4. Документ Markdown: набранный заголовок отображается в предпросмотре у
   другого участника.
5. Фигура, нарисованная на доске, появляется у другого участника, а отмена
   (undo) убирает её у обоих.
6. Запуск кода: результат выполнения виден всем участникам (требует запущенного
   runner и Docker; включается переменной `E2E_RUNNER=1`).
7. Интерфейс: файл создаётся через диалог в боковой панели, выбранная тема
   переключается и сохраняется после перезагрузки страницы.

8. Импорт: публичный репозиторий GitHub вставляется ссылкой при создании проекта,
   его файл появляется в проекте, а содержимое — в редакторе (нужен доступ в
   интернет; без него тест пропускается).

9. Удаление файла из боковой панели с подтверждением.
10. Неверный токен GitHub: запрос доходит до настоящего API GitHub, пользователь
    видит понятное объяснение ещё до отправки, кнопка «Отправить» недоступна (нужен
    доступ в интернет).
11. Файлы показываются в папках, папки сворачиваются.
12. Проект удаляет владелец, а гость его покидает — проект исчезает из списка.
13. Запуск кода импортирует соседний файл проекта (`require('./logger')`).
14. Ссылка-приглашение показывает проект и владельца, гость вводит имя и попадает в проект.
15. Неизвестная ссылка и недоступный проект объясняют, что произошло.
16. Владелец меняет роль участника и убирает его из проекта.
17. Человек меняет своё имя.
18. Файл находится по Ctrl+P и переименовывается из боковой панели.
19. Проект с файлами открывается на README, заголовок вкладки называет файл.
20. Открытые файлы становятся вкладками: переключение и закрытие.
21. Ветки: владелец переключает импортированный репозиторий на другую ветку, и у
    второго участника список файлов меняется без перезагрузки; возврат на основную
    ветку возвращает её файлы (нужен доступ в интернет).
22. Терминал: в панели появляется приглашение bash, команда `ls && node main.js`
    показывает файл проекта и результат его выполнения; Ctrl+\` закрывает панель
    (нужны runner и Docker, `E2E_RUNNER=1`).
Сценарий 9 дополнен корзиной: удалённый файл возвращается кнопкой «Восстановить».

Успешная отправка коммита проверена только на имитации GitHub в модульных тестах:
проверять на настоящем репозитории пришлось бы с чьим-то токеном.

Отдельный «тест» `screenshots.spec.ts` не проверяет поведение, а создаёт
скриншоты интерфейса для диплома (запускается только с `SCREENSHOTS=1`).

Каждый сценарий создаёт собственных пользователей и проект, поэтому тесты не
зависят друг от друга. Прогон всего набора занимает около 70 секунд. Тесты используют базу Redis №1, чтобы runner, запущенный для разработки (база 0), не подхватывал их задачи.

**Результаты прогонов.** При локальных прогонах набор проходил полностью.
Тест чата с присутствием дважды упал в полных прогонах, когда машина была
занята другими задачами, и не воспроизводился ни в 20 одиночных повторах, ни в
4 полных прогонах подряд, ни в стресс-прогоне (24 повтора в 6 параллельных
потоках — все прошли). Разбор кода хаба присутствия и WebSocket-клиента гонки,
объясняющей сбой, не выявил; наиболее вероятная причина — перегрузка машины, но
это предположение. В CI для e2e включён один повтор упавшего теста.

## 5.3. Безопасность запуска кода

Запуск произвольного кода — самая опасная функция платформы, поэтому она
изолирована и ограничена (подробности и альтернативы — ADR-003):

| Мера | Реализация |
|---|---|
| Нет сети | `--network none` |
| Файловая система только для чтения | `--read-only`, для временных файлов `tmpfs /tmp` на 16 МБ |
| Непривилегированный пользователь | `--user 65534:65534` |
| Без привилегий ядра | `--cap-drop ALL`, `--security-opt no-new-privileges` |
| Лимит памяти | 128 МБ (без swap) |
| Лимит процессора | 0,5 ядра |
| Лимит процессов | 64 (защита от fork-бомбы) |
| Время | 10 секунд, затем принудительная остановка контейнера (`docker kill`) |
| Вывод | не более 64 КБ, остальное отбрасывается |
| Хост не затрагивается | проект передаётся tar-архивом через stdin и распаковывается в tmpfs контейнера; имя файла передаётся переменной окружения |
| Только список разрешённых языков | JavaScript и Python; другие значения отклоняются до запуска |
| Права | запускать код может только участник проекта с ролью не ниже `editor` |

В тестах с настоящим Docker проверены: отсутствие сети, невозможность записи в
корневую файловую систему, работа от непривилегированного пользователя,
остановка бесконечного цикла по таймауту, усечение огромного вывода, а также
то, что набор флагов `docker run` содержит все перечисленные ограничения.
Лимиты памяти, процессора и числа процессов проверены на уровне аргументов
запуска, но не нагрузочными тестами (например, настоящей fork-бомбой).

Терминал (п. 3.6) работает в контейнере с теми же мерами (нет сети, корневая система
только для чтения, `nobody`, без capabilities), но с лимитами на сеанс: 256 МБ памяти,
128 процессов, 30 минут жизни контейнера. Доступ к нему даёт одноразовый билет,
который выдаёт API после проверки роли и (на публичном адресе) кода доступа; сам
сервер терминалов не принимает ни токенов, ни идентификаторов проекта от браузера.
Тесты с настоящим Docker проверяют отсутствие сети, невозможность записи вне
`/project` и `/tmp`, пользователя `nobody` и прерывание программы по Ctrl+C.

**Что не покрыто.** Контейнер использует ядро хоста: уязвимость побега из
контейнера (kernel escape) защитой не закрыта. Для публичного запуска
недоверенного кода это решается усилением изоляции (gVisor, Firecracker),
что вне объёма работы; платформа ориентирована на приглашённых участников
проекта, а не на анонимный публичный запуск, и запуск кода — лишь
вспомогательная функция.

## 5.4. Безопасность доступа

- Пароли хранятся как хеши `argon2id`; access-токены — короткоживущие JWT;
  refresh-токены — непрозрачные случайные значения, в базе хранится только их
  хеш, при каждом использовании выдаётся новый (ротация).
- Пользователь, не состоящий в проекте, получает `404`, а не `403`: ответ не
  раскрывает, что проект существует.
- Роли `owner > editor > viewer` проверяются на сервере: и в REST API, и при
  подключении к серверу синхронизации (для `viewer` соединение read-only, сервер
  не принимает и не сохраняет его правки). Локальная копия документа у
  наблюдателя технически изменяема, но изменения не уходят на сервер и не
  попадают другим — это проверено сквозным тестом (п. 5.2, сценарий 2).
- WebSocket `/ws` проверяет JWT и членство в проекте до подписки; при ошибке
  закрывается с кодом 4401 или 4403.
- Цвет и имя чужого курсора приходят от другого клиента и попадают в
  динамически создаваемый CSS; значения цвета проходят строгую проверку
  (`#rrggbb`), имя экранируется — это защита от внедрения стилей (тест в
  `cursor-styles.test.ts`). По той же причине экспорт доски в SVG экранирует
  текст и принимает только безопасные цвета.
- Гостевой вход создаёт временного пользователя без пароля; гость получает
  только те права, которые даёт ссылка-приглашение.

## 5.5. Что проверено вручную, а что нет

| Область | Состояние |
|---|---|
| Совместное редактирование, роли, приглашения, гости, чат, присутствие | Проверено автоматически и в браузере |
| Доска, Markdown-предпросмотр, курсоры | Проверено автоматически (доска и Markdown — E2E; курсоры — модульные тесты на генерацию стилей); курсор другого участника с именем виден на скриншотах интерфейса (п. 2.5) |
| Сборка фронтенда (PWA) | Собирается; service worker и precache (около 13 МБ) создаются |
| Работа PWA без сети (офлайн-запуск приложения) | **Не проверено** в браузере: E2E-теста нет, полагаемся на штатное поведение workbox |
| Образы Docker api / collab / runner | Собираются; `api` запущен и отвечает (п. 5.6); полный `docker-compose` не разворачивался |
| Деплой на AWS | **Не проверен** на реальном аккаунте; `docs/deploy-aws.md` — инструкция, а не отчёт о развёртывании |
| Нагрузка в браузерах | Не измерялась (исследование — на Node-клиентах, глава 4) |

## 5.6. Сборка контейнеров

Образы сервисов собираются одним `infra/docker/Dockerfile` (цели `app` и
`runner`, аргумент `APP`). Проверено локально: образы `api`, `collab` и
`runner` собираются; образ `api` запущен с реальными PostgreSQL и Redis и
отвечает на запросы (`/docs/json` — 200); в образе `runner` доступен клиент
Docker. В ходе проверки найдена и исправлена ошибка: для `runner` выполнялась
генерация Prisma-клиента, от которого он не зависит. Полный стек через
`docker-compose` на сервере (Caddy, миграции, RDS, S3/CloudFront) не
разворачивался.
